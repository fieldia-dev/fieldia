Fieldia Maps

A new package, @fieldia/map, with the map features apps usually spend weeks building, ready to use. Any map provider. Pins and cards are described by the page. Places and areas can be fields on a form. Records go on a map beside their list. Routes with a driver on the way. Positions that move live. Areas coloured by their numbers.

How it stacks

One map engine, Leaflet (about 40 KB compressed, BSD-licensed), drawn by Fieldia's own code. Each provider plugs in underneath, and every feature sits on top of the same engine. A feature the chosen provider can't do is hidden, with a line saying why.

On a formPlace field (a point) · Area field (a drawn shape) · a map of a record's points, its route and live positions
Beside a listRecords as pins, bubbles, cards, choosing pins, "search this area", a drawn area as a filter
LayersPins · routes · coloured areas · heat map — each described by the page, any number on one map
Map corePan and zoom, keyboard, finger and pen, right to left, Fieldia's themes and dark scheme, attribution, languages
ProvidersMap images · address search · routes · reachable area — each from Azure Maps, Google, Mapbox, a self-hosted server, or the app's own function

The parts

The page uses the words Fieldia already uses: a field node with a widget and options, an option ending in Field names a field, colours by condition as table rows have them, and a card is a small layout of the record. Anything the page can't describe, the app draws with its own widget, as it can for fields and, since 0.13.1, for table columns.

1 · Place field

A point on a form: click the map, drag the pin, search an address, or press "My location". The point is saved to two number fields, the way Odoo stores a partner's place.

  • Address search goes through the app's geocoder, so Fieldia holds no keys.
  • Latitude and longitude stay typeable: that is the keyboard and screen-reader way in.
  • Optional: fill an address field from the point (reverse search).
  • Read-only shows the pin and nothing to drag.
{ type: 'field', id: 'where', field: 'latitude', widget: 'place',
  options: { longitudeField: 'longitude', addressField: 'street',
             myLocation: true, zoom: 16 } }

2 · Area field

A shape on a form, such as a delivery zone or a service area: a polygon, a box or a circle. It's saved as GeoJSON in a json field.

  • Grips to reshape it, and the whole shape drags to move.
  • Enter finishes, Escape gives up, Backspace takes back a point.
  • Works the same by mouse, finger and pen (pointer events).
  • A hint bar says what to do at each step; Clear removes the shape.
  • A list of named areas can stand in for drawing, for keyboard use.
{ type: 'field', id: 'zone', field: 'zone', widget: 'area',
  options: { shapes: ['polygon', 'box', 'circle'], one: true } }

// saved value (GeoJSON):
{ "type": "Polygon", "coordinates": [[[31.21, 30.04], …]] }

3 · Pins, labels and cards

What every pin looks like, from the record's fields:

  • look: a pin, an icon, a round photo, a label only, or a dot
  • icon: a fixed one, or one chosen by a field (car / scooter / bike)
  • image: an image field, such as a driver's photo
  • label: any field, written as its type is written ("9.5M", "4 min", "Table 12")
  • tones: colour by condition
  • turn: a field in degrees, so a car faces its way
  • widget: the app draws the pin itself

The card a pin opens is a small layout of the same record: fields, an image, words and buttons, the same parts a form uses. It can be left out, or drawn by the app's own widget. Hovering can open it on a desktop; on a phone a tap does.

pin: { look: 'icon', icon: 'car', turn: 'heading', label: 'name',
       tones: [{ when: [['status', '=', 'busy']], tone: 'muted' }] },
card: [ { field: 'driver_photo' }, { field: 'name' },
        { field: 'rating' }, { button: 'assign' } ],
cluster: { label: 'count' }   // or false

// anything else:
pin: { widget: 'my-pin' }     // the app's own, from mountViewer({ widgets })

4 · Records on a map, beside the list

The list page gains a map view. Its pins come from the data source.

  • Moving the map asks for what is in view; "Search this area" turns the view into a filter in the search bar.
  • A drawn area becomes a filter too, and it can be saved as a favourite like any other.
  • Pins chosen on the map, with a tick or a lasso, feed the list's buttons for chosen records.
  • Hovering a row lights its pin, and hovering a pin lights its row.
  • Bubbles: drawn by Fieldia from the pins it has, or sent ready-grouped by the app's server when there are many thousands.

New in the data source: an optional "records in this area" call. A source without it can still show its records, but the area filter is hidden.

// the data source, optional:
searchArea({ model, area, filters, zoom })
  → { records, clusters? }

// the list page:
views: ['list', 'map'],
map: { at: { latitude: 'lat', longitude: 'lng' },
       pin: { look: 'label', label: 'price',
              tones: [{ when: [['offer', '=', 'rent']], tone: 'info' }] },
       card: [{ field: 'photo' }, { field: 'name' }, { field: 'price' }] }

5 · Several kinds of point on one record

A map on a form can show any number of layers from one record: its own fields (the kitchen, the door, the courier), its lines (a delivery round's stops, in order), or related records. Each layer has its own pin and its own card.

{ type: 'map', id: 'order-map', layers: [
  { id: 'kitchen', at: { latitude: 'kitchen_lat', longitude: 'kitchen_lng' },
    pin: { look: 'icon', icon: 'shop' } },
  { id: 'door', at: { latitude: 'lat', longitude: 'lng' },
    pin: { look: 'icon', icon: 'home' } },
  { id: 'courier', at: { latitude: 'courier_lat', longitude: 'courier_lng',
                         heading: 'courier_heading' },
    pin: { look: 'photo', image: 'courier_photo', label: 'eta_text' } },
  { id: 'stops', lines: 'stop_ids', pin: { look: 'pin', label: 'sequence' } },
] }

6 · Positions that move

When a point's fields change, its pin glides to the new spot along the shortest path on screen, or along the route when there is one. The map never redraws.

  • The app sends new positions with setValues today. Later, an optional data-source call can stream changes.
  • "Last seen 2 min ago" shows when a position goes stale (the page sets after how long).
  • Following a pin keeps it in view as it moves, until the person pans away.
handle.setValues({ courier_lat: 30.0512, courier_lng: 31.2337,
                   courier_heading: 84 });

layers: [{ id: 'courier', …, live: { staleAfter: 120, follow: true } }]

7 · Routes

A line along the roads between points: from the courier to my door, or through a round's stops in order.

  • "My location" comes from the browser once the person allows it, or from a typed address.
  • Live progress: the part already driven fades, and the time and distance left become values for labels and cards.
  • A new route is fetched when the driver leaves the old one.
  • A route's distance, time and roads can be saved on the record. That's the ground for later features: price by distance, a "running late" warning, proof of the route driven.
  • Routes come from the provider, or from the app's own function.
{ id: 'way', route: { from: 'courier', to: 'door', mode: 'car' },
  progress: true,
  write: { seconds: 'eta_seconds', metres: 'distance_m',
           line: 'route_geojson' } }

// the provider or the app gives:
route({ from, to, via, mode }) → { line, metres, seconds }

8 · Areas by colour

Municipalities, districts or zones, shaded by category or by a number, with a legend.

  • Hover brightens an area and shows its card (the page decides what is on it).
  • A click filters the records to that area, or chooses it as a field's value ("which district").
  • Borders come as GeoJSON from the app: a file, a field or a function. Fieldia doesn't ship borders; the docs point to open sources such as OpenStreetMap and geoBoundaries.
  • Colours come from Fieldia's theme and pass contrast in light and dark.
{ id: 'districts',
  regions: { from: '/geo/districts.json', key: 'code' },
  colour: { by: 'orders_week', scale: 'sequential', legend: true },
  hover: { card: [{ field: 'name' }, { field: 'orders_week' }] },
  click: 'filter' }   // or { choose: 'district_id' }

9 · The rest of the box

  • Heat map where pins are too many to read.
  • Nearest first: sort a list by distance from a point, such as my location.
  • Reachable area: "within 15 minutes' drive" as an area, from providers that compute it.
  • Geofences: "courier entered the zone" runs the page's own steps, the same steps a button runs.
  • Base maps: road, satellite and traffic, where the provider has them.
  • Measure a distance, and full screen.
map: { heat: { weight: 'orders' },
       baseMaps: ['road', 'satellite', 'traffic'],
       tools: ['measure', 'fullscreen'] }

layers: [{ id: 'reach', reachable: { from: 'kitchen', minutes: 15 } }]

geofences: [{ area: 'zone', when: 'enter', layer: 'courier',
              run: [{ action: 'notify_customer' }] }]

How each part is proved

The same rules as every Fieldia release, plus what maps need on top.

Test first, and see it fail

Every browser test is written before the code and fails first. Each one is also run once with its fix taken out, to prove it would catch the bug.

Used the way people use it

Drawn and dragged by mouse at hand speed, by finger (touch emulation), and by keyboard alone. Typed into, never only read. Screenshots of each part open are looked at, not just taken.

Every look

Light and dark, all eight themes, an Arabic page right to left. Accessibility checks (axe) on every demo, and contrast checks on labels over the map and on area colours.

Stand-in providers

Tests never call a real provider. Each stand-in returns exactly the shape the real one does, errors included, taken from that provider's reference. A short manual check against each real provider runs before a release.

Size

The main script doesn't grow. @fieldia/map gets its own size budget, checked in CI. Provider adapters load only when used.

Release check

Installed from the packs into an empty project: require, import and types all check, as for the other ten packages.

The hard part is a map without a mouse. Panning and zooming by keys is easy. Pins become a list in reading order: Tab moves through them, Enter opens the card. Drawing a polygon by keyboard is not realistic, so the Area field always offers a list of named areas or typed coordinates beside the drawing tools. Screen readers get the same list, and the map itself is described ("12 homes in view").

Decisions

All five taken on 11 October, as recommended.

  1. Map engine: Leaflet or MapLibreLeaflet draws map images: small, simple, works everywhere. MapLibre draws vector maps with WebGL: smoother zoom and rotation, but about six times larger and harder on old phones. Decided: Leaflet now. The core is written so MapLibre could be added later as a second engine.
  2. Google: Map Tiles API only, or also Google's own JavaScript mapThe Map Tiles API fits the same engine as the others. Google's own map would be a second, larger adapter for apps that must use it. Decided: Map Tiles API first; the second adapter only if an app asks.
  3. KeysThe app can pass a key in the browser, restricted to its site, or a URL on its own server that hands out short-lived tokens. Decided: support both; the docs and demos show the token URL.
  4. Where to startPhases 1 and 2 give the most-asked-for parts (fields, a property-style search). Phase 3 is what makes it stand out (live courier, routes). Decided: in order, 1 → 4, releasing after each.
  5. Our own sitesOnce phase 2 ships, the property map we run today could move onto it and drop its own map code. Decided: yes, after phase 2, as a separate task.

Fieldia is MIT-licensed and public: this plan names no private product, and its code will be written fresh. Sources for the provider rules: Google Map Tiles API policies, Google Map Tiles session tokens, OpenStreetMap tile usage policy, Azure Maps Route API migration.
